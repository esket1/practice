### User Stories
Как [роль], я хочу [действие], чтобы [выгода]

US-1. Регистрация, вход, выход, сброс пароля
Как преподаватель, я хочу зарегистрироваться по email, входить, выходить и сбрасывать забытый пароль, чтобы иметь доступ к ИС.
AC:
- Регистрация: email + пароль + ФИО; email уникален; пароль ≥ 8 символов, хранится только хэшем.
- Вход возвращает JWT access + refresh; выход refresh.
- Сброс забытого пароля: ссылка выводится в лог, переход - новый пароль - UPDATE password_hash; токен в БД не хранится.
- Ошибки входа не должны расскрывать существует ли email.
- Клиент валидирует только формат, серверр валидирует все.

US-2. Управление пользователями, ролями и блокировками
Как администратор, я хочу видеть список пользователей, менять роли, блокировать/разблокировать и видеть историю блокировок, чтобы контролировать и разграничивать доступ к ИС.
AC (список):
- Пагинация, поиск по email/ФИО, сортировка, фильтр по роли и статусу блокировки на сервере.
- Доступ только админу.

AC (роли):
1. teacher
2. assistant
3. admin; 

- Проверка прав на сервере на каждом эндпоинте.
- Нельзя снять роль у последнего активного админа.

AC (блокировка):
- Блокировка создаёт запись в UserBlock (user_id, blocked_by_id, blocked_at, reason not null).
- Разблокировка создаёт запись в UserUnblock (block_id unique, unblocked_by_id, unblocked_at); запись в UserBlock не редактируется и не удаляется.
- Активная блокировка = 403.
- Нельзя заблокировать самого себя и последнего с ролью админа.

AC (история блокировок):

История = UserBlock LEFT JOIN UserUnblock по user_id, сортировка blocked_at DESC, пагинация на сервере.

Записи append-only.

US-3. Ведение каталога оборудования и справочников
Как лаборант/администратор, я хочу управлять оборудованием и справочниками (категории, локации, статусы), чтобы каталог соответствовал реальности.

AC — оборудование:

CRUD: название, инвентарный номер (UNIQUE), категория, локация, статус, фото.

Удаление — только с подтверждением; при активной выдаче (Assignment без Return) → 409.

Валидация на клиенте и сервере с понятными ошибками.

AC — справочники:

CRUD для Category, Location, Status — только админ (RBAC на сервере).

Удаление — с подтверждением; нельзя удалить запись, на которую ссылается Equipment → 409 (ON DELETE RESTRICT).

name уникально (UNIQUE в БД).

Списки — пагинация/поиск/сортировка на сервере.

US-4. Поиск и фильтрация оборудования
Как преподаватель, я хочу находить оборудование по фильтрам, чтобы быстро понять, что доступно.

AC:

Пагинация, поиск по названию/инвентарному номеру, сортировка по нескольким полям — на сервере.

Фильтры: категория, локация, статус.

Ответ < 500 мс на seed-данных (индексы на name, inventory_number, status_id, category_id, location_id).

Пустой результат → состояние «ничего не найдено».

US-5. Фото оборудования
Как лаборант, я хочу прикреплять фото к оборудованию, чтобы проверять состояние при возврате и опознавать его.

AC:

Только image/jpeg, image/png, image/webp, ≤ 5 МБ.

Проверка типа и размера на сервере.

Файл хранится вне БД; в Equipment.photo_url — ссылка.

Невалидный файл → 400 с понятным сообщением; превью в карточке.

US-6. Движение оборудования: выдача, возврат, перемещение
Как лаборант, я хочу выдавать оборудование преподавателю, принимать обратно и перемещать между локациями, чтобы фиксировать статус и местоположение.

AC — выдача:

Создаётся Assignment (equipment_id, user_id — получатель с ролью teacher, issued_by_id = текущий лаборант, issued_at, due_at).

Получатель — только пользователь с ролью teacher (проверка на сервере).

Нельзя выдать занятое (Assignment без Return) → 409.

Assignment + смена статуса на issued + запись в MovementHistory (action='issued') — одна транзакция.

due_at > issued_at.

AC — возврат:

Создаётся Return (assignment_id UNIQUE, returned_at, accepted_by_id).

Двойной возврат блокируется UNIQUE; возврат невыданного → 409.

Return + статус на available + MovementHistory (action='returned') — одна транзакция.

returned_at >= Assignment.issued_at.

AC — перемещение:

Смена Equipment.location_id + MovementHistory (action='moved', from_location_id, to_location_id) — одна транзакция.

Нельзя переместить выданное → 409; from_location_id != to_location_id.

US-7. Дашборд со сводной статистикой
Как администратор/лаборант, я хочу видеть сводку по оборудованию и графики, чтобы контролировать состояние и просрочки.

AC:

Сводка по статусам: GROUP BY status (всего/доступно/выдано/в ремонте/списано).

График по категориям.

Просроченные выдачи: Assignment LEFT JOIN Return WHERE Return.id IS NULL AND due_at < now().

Активные блокировки: UserBlock LEFT JOIN UserUnblock WHERE UserUnblock.id IS NULL.

Данные — с сервера, отдельный эндпоинт.

US-8. История взаимодействий с оборудованием
Как администратор, я хочу видеть полную историю взаимодействий с оборудованием, чтобы расследовать пропажи и поломки.

AC:

Все действия пишутся в MovementHistory: issued, returned, moved.

Каждая запись: equipment_id, user_id, from_location_id/to_location_id (nullable, если сторона не применима), action, created_at.

MovementHistory — append-only (UPDATE/DELETE запрещены триггером и сервисом).

Фильтры: оборудование, пользователь, тип действия, дата; пагинация и сортировка — на сервере.

Запись создаётся в той же транзакции, что и основное действие (US-6).

US-9. Личный кабинет пользователя
Как преподаватель, я хочу видеть профиль, менять пароль и смотреть историю своих выдач, чтобы контролировать, что у меня на руках.

AC:

Профиль: ФИО, email (read-only), роль.

Смена пароля: старый обязателен, новый ≥ 8 символов, хэшируется; не путать со сбросом забытого пароля (US-1).

История моих выдач: Assignment LEFT JOIN Return WHERE user_id = current_user, пагинация на сервере.

Активные выдачи с флагом «просрочено» (due_at < now() и Return нет).

Только свои данные: user_id = current_user проверяется на сервере; чужие → 403.

US-10. Журнал аудита действий
Как администратор, я хочу видеть полный журнал действий пользователей, чтобы разбираться в спорных ситуациях.

AC:

Журнал = MovementHistory + UserBlock/UserUnblock (агрегированное представление).

Фильтры: пользователь, тип действия, дата; пагинация и сортировка — на сервере.

Append-only: записи не редактируются и не удаляются.

Доступ только админу (RBAC на сервере).
